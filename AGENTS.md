# Working rules
- Never guess how code, config or the system works. Run a command to find out
  (ls, grep, cat, git log, --help) before answering.
- Take one small action at a time, then look at the result.
- If a requirement is ambiguous, ask me one short question instead of choosing.
- Do not explain your plan at length. Act, then report briefly.
- Prefer reading real files over relying on memory of APIs.
- Commit messages follow `docs/commits.md`.

## Comments
- A comment says why, or says nothing. The file already says what.
- Keep it to one line, and to the shortest wording that still carries the reason.
- Document a feature in the README, not in the file that turns it on.
- Do not summarise the README in a comment, and do not restate the code.
- Say where something else lives, not why it lives there too.
